# Peer-Project Synthesis

## Method

Each peer was treated as evidence, not as an architecture to merge wholesale. Every file was hashed and classified. Independently meaningful mechanisms received adopted, adapted, hardened, extracted, recomposed, synthesized, inspired-native, guardrail-derived, superseded, rejected-with-reason, or reference-only dispositions. The target's existing execution engine and risk authority were preserved.

## Material synthesis choices

- **Many-to-one:** multiple donor strategy/backtest concepts became one declarative strategy and validation plane.
- **Many-to-many:** provider resilience, dataset provenance, instrument normalization, and workload controls were decomposed and recomposed across market, dataset, workflow, and risk owners.
- **One-to-many:** security lessons from provider/tool implementations became SSRF controls, secret-reference policy, bounded tools, API secondary credentials, tests, and runbook requirements.
- **Negative-to-guardrail:** arbitrary code execution, plaintext secrets, implicit authority, unbounded retries, weak audit trails, and UI-driven authority became explicit prohibitions and tests.
- **Superseded:** donor execution engines, process supervision, monitoring, RL training, and broker adapters were not duplicated where the target already had a stronger authoritative owner.
- **Reference-only:** media, branding, generated files, examples, and low-fit implementation details remain accounted for without entering runtime code.

## Licence posture

MIT- or Apache-licensed peers supplied evidence and mechanisms; uncertain or absent licence surfaces were used only for independently derived concepts and negative lessons. No donor source file lacking a compatible, explicit licence was transplanted into runtime. Exact paths, hashes, licence notes, transformations, and target ownership are in the release evidence bundle.
